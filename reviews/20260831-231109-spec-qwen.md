## Review of `spec/0004-names-with-owners`

### 1. Coherence and internal consistency

The spec is largely coherent. The separation between **registered**, **reserved**, and **durable** is clear in `SPEC.md` §2, and the slice boundary is explicit in `SPEC.md` §7: slice 1 closes the reconnect window, while slice 2 is specified but not built. `SPEC.md` §4 correctly warns that no reconnect test is evidence about the restart column, and `acceptance/CASES.md` mirrors that by defining **D-1** as a slice-2 case and stating that a green slice-1 suite is not evidence about **D-1**.

There are some non-blocking ambiguities and missing edge cases:

- `SPEC.md` §5.1 says `Check` treats a short token as no token, while `SPEC.md` §5.3 says a request “with a token of at least `MinTokenLen` calls `Claim`; one without calls `Check`.” A request with a short but present token is therefore only indirectly covered.
- `SPEC.md` §5.1’s `Claim` policy is per-subdomain. It does not explicitly prevent two different subdomains from claiming the same `TCPPort`, nor does it specify rollback if a later port allocation fails. This is an edge case the acceptance tests do not exercise.
- `SPEC.md` §2 says a reservation dies “never, until released or expired,” but slice 1 has no release operation and no expiry. This is partly explained by the slice model, but the wording is still tense with the in-memory nature of slice 1.

These are worth correcting, but I do not treat them alone as blocking.

### 2. Edge cases the acceptance tests miss

The acceptance suite misses several end-to-end edges:

- A short token presented through the relay, not just through `core.Claim`; only **R-4** covers the core level.
- Two different claimed names attempting to reserve the same public TCP port.
- An owner reconnecting without requesting the previously reserved port, or requesting port `0`.
- Explicit release or abandonment semantics in slice 1.

Again, these are gaps, but the decisive problem below is the L-006-style acceptance defect.

### 3. Conformance to the charter, as far as reproduced material shows

From the reproduced material, the spec appears to follow the procedural disclosures it itself makes:

- `INTENT.md` acknowledges the 24-hour veto window and states that `Alpha` / CHARTER Part 0 makes the window non-blocking.
- `acceptance/CASES.md` states the cases are frozen and that the builder may not edit them.
- The slice-2 case **D-1** is deliberately left specified-but-unbuilt rather than being silently omitted.

I find no citable charter violation from the text provided.

### 4. Whether the spec matches its intent statement

The intent statement in `INTENT.md` distinguishes the reconnect gap from relay restart and says the product should make the address survive, while the connection never survives. `SPEC.md` §4 and §7 preserve that distinction and do not overclaim that slice 1 delivers restart durability. In that respect the spec matches its intent.

### 5. L-006: acceptance case that can pass without exercising the clause it names

The blocking defect is **C-4** in `acceptance/CASES.md`.

`acceptance/CASES.md`, case **C-4**, says:

> **C-4** | **`Tunnel.Reserved` is read by something.** The relay's status view reports a claimed tunnel as reserved and an anonymous one as not. | `relay.TestTheStatusSurfaceReportsWhoOwnsAName` | The field is written and read nowhere — `grep -rn "\.Reserved" --include=*.go` returning nothing is the state at `1853218`...

`SPEC.md` §5.3 requires:

> `tunnel.Reserved` is set from `Reservations.Get(name)` ... It is read by `relay/dashboard.go`'s status view as a `"reserved"` field, so `grep -rn "\.Reserved"` stops returning nothing.

But the named Go test, `relay.TestTheStatusSurfaceReportsWhoOwnsAName`, is described only as a status-surface test. A status surface could report reservation state by consulting `Reservations.Get` directly, while `Tunnel.Reserved` remains written and never read. In that situation the status test can pass, yet the clause named by **C-4** — that `Tunnel.Reserved` is read by something — remains false. The case therefore can pass without exercising the clause it names, which is precisely the defect class identified by lessons/L-006.
