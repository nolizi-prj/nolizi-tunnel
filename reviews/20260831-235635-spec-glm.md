### Objection 1 — §5.1 and §11 contradict each other in a reachable, common state, and no frozen case can fail on it

SPEC.md §5.1: "if anything after that fails — **the registry refuses the name as live**, the bind fails, the announce fails — the relay calls `Discard` for a claim created by that handshake. So **a name is never consumed by a connection that never opened**."

SPEC.md §11: "**The fix** is one guard: `discardClaim` returns early **if the registry still has the name**."

The guard fires on exactly the first-listed §5.1 trigger, unconditionally. Walk the state: an anonymous agent holds a live tunnel on name *N* (per §6 row 2, anonymous registrations are never `Reserved`, so *N* is live in the registry and unclaimed in the reservation set — this is the normal state of every anonymous tunnel). A token-holder arrives naming *N*: `authorize` calls `Claim` (§5.3 — Claim precedes any liveness check; §2 and §11's own race narrative confirm Register is later), which succeeds, `created=true`. `Register` then refuses `ErrNameTaken`. §5.1 mandates `Discard`; §11's guard suppresses it, because the registry has *N* — but the registrant is a **stranger**, not a co-claimant of the same token, which is the only case §11's hazard analysis contemplates. The claim persists: *N* is consumed by a handshake that never opened, in the very sense §5.1 declares impossible and C-7 exists to prevent — and C-7 exercises only the registry-empty path (the public port is bound, so nothing is live on `bindfail`). §11's in-package test asserts the guarded branch as correct (register a tunnel on a claimed name → guard holds), so it cannot catch this either; its two poles — claimant-registered and nothing-registered — sit either side of the stranger-registered state.

This is not exotic: it is the *first* thing that happens the first time a user shows up with a token for a name an anonymous agent is squatting. The resulting behaviour is arguably good (the token-holder keeps the claim and wins the name at the squatter's next disconnect, which §6's "unless someone else has claimed that name" sanctions) — but the spec's clauses then disagree about it: §5.1's invariant is false, §5.1's mandated Discard is a no-op, and §11's gloss ("a claim is undone only when nothing is using it") is false too, since the stranger's tunnel is using the *registry entry*, not the *claim* — the exact conflation §2 warns is a rule fork (L-007). By the bar this spec set itself in §9 (a "real inconsistency" in one sentence of §2 warranted an amendment), a head-on clause collision in a common state warrants the same remedy: amend in the open, fresh review.

Corollary that the same guard breaks: §9's premise for narrowing C-4 — "the reservation set and a live tunnel's `Reserved` field agree in every reachable slice-1 state" — was true under §5 alone. With §11's guard, the squatter's tunnel was registered before the claim, so its stored `Reserved` is false while the record claims *N*: the two sources disagree on a shipped surface (§5.3's status view reads the stale `Tunnel`), and no execution distinguishes the correct implementation from M3b in that state either. §11 was written after §9 and broke its premise without reconciling it.

### Objection 2 — §5.2 specifies a held state that no clause ever tells the relay to enter

§5.2 introduces `Hold`/`Unhold`/`Holder` and the held state, then assigns them **no caller**: §5.3 changes only `authorize`, and §5.2's only sentence about the disconnect side is that `releaseTCP`'s `ReleaseOwner` "moves together" with the owner-string change — a wording change, not the load-bearing transition. The one clause that closes window (a) for the port — *when does a disconnecting tenant's port become held?* — is nowhere written. And the frozen suite cannot falsify it: C-2 is satisfied equally by "released to held" and by a relay that **never releases at all** (port left `inUse` keyed by subdomain: the anonymous agent still gets `ErrPortPoolExhausted`, the owner's `AllocateSpecific` still re-grants); C-7 discards a claim but never observes the port afterwards, so "the discarded claim's port returns to the pool" is asserted by no case and no clause. Under that leak, every frozen case is green while §5.2's held state is inert at the relay — the precise §2 defect (`Tunnel.Reserved` at `1853218`), reintroduced one type over. §10's M2 row ("all three RED") is true only of the unstated design. The existing pre-0004 suite may pin release-to-free — but by this packet's own rule (CASES.md, L-006) that suite is not an acceptance case for this spec, and if it does pin it, slice 1 reddens it, which §12's "no frozen case from 0001–0003 is touched" does not address.

The spec's substance, slicing honesty, and per-case testability are strong; the guard/rollback contradiction and the unpinned port-hold transition are coherence failures in exactly the family §§9–12 exist to police, and both need an in-the-open amendment plus a fresh review before freeze.

VERDICT: OBJECT — SPEC.md §5.1 ("the registry refuses the name as live … the relay calls Discard … a name is never consumed by a connection that never opened") is contradicted by SPEC.md §11 ("discardClaim returns early if the registry still has the name") whenever the live registration is a stranger's — every anonymous tunnel on an unclaimed name plus a token-holder's failed `ErrNameTaken` handshake leaves the claim permanently in place, the name consumed by a connection that never opened, and no frozen case (acceptance/CASES.md C-7 exercises only the registry-empty path; §11's in-package test asserts the guarded branch as correct) can fail on it.
