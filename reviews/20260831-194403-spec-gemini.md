## 1. Coherence and Internal Consistency

- **Multiplexer Write Ordering vs. Reader Contention ([`SPEC.md` §2](file:///home/m/dev/pumasi-tunnel/spec/0003-session-before-announce/SPEC.md#L27-L57)):**  
  The specification correctly corrects the legacy analysis from `spec/0002`. In `spec/0002`, it was asserted that `mux.Server(conn)` could not precede the handshake response due to reader contention. `SPEC.md` §2 demonstrates that reader contention is non-existent because the connecting agent sends no data between its auth request and its first stream frame. The true hazard is on the write side: `mux.Session.Open` transmits `FrameOpen` under `Session.writeMu` on the shared connection `conn`, while the announce frame (`okFrame`) is written unmanaged. A naive reordering (inserting the session in `r.sessions` prior to `writeFrame`) introduces a race where concurrent visitor traffic can place a `FrameOpen` onto the wire ahead of `okFrame`, causing the agent’s `core.DecodeAuthResponse` to fail and drop the connection.

- **Dual-Purpose Lock Synchronization ([`SPEC.md` §3.1](file:///home/m/dev/pumasi-tunnel/spec/0003-session-before-announce/SPEC.md#L58-L87)):**  
  The change uses the existing `r.mu` (`sync.RWMutex`) in [`relay/relay.go`](file:///home/m/dev/pumasi-tunnel/relay/relay.go#L222-L236) to solve both ordering and wire exclusion:
  1. *Ordering:* `ServeHTTP` acquires `r.mu.RLock()`, ensuring visitor dispatch blocks while `ServeAgent` holds `r.mu.Lock()` during session insertion and auth-response transmission.
  2. *Exclusion:* Visitors cannot acquire a session handle or invoke `OpenStream` until `r.mu.Unlock()` executes, guaranteeing that `okFrame` is always the first frame on the agent's connection.

- **Lock Contention & Bounded Latency ([`SPEC.md` §3.2](file:///home/m/dev/pumasi-tunnel/spec/0003-session-before-announce/SPEC.md#L88-L112)):**  
  Holding `r.mu.Lock()` across a socket write is bounded by three invariants: the small frame size (< 4096 bytes) buffered by the kernel TCP send buffer, the handshake deadline (`conn.SetDeadline(now + HandshakeTimeout)`) remaining active across the write, and zero allocations or network reads under the lock.

## 3. Acceptance Cases & L-006 Verification ([`lessons/L-006`](file:///home/m/dev/pumasi/lessons/L-006-tests-that-cannot-fail.md))

The acceptance cases defined in [`acceptance/CASES.md`](file:///home/m/dev/pumasi-tunnel/spec/0003-session-before-announce/acceptance/CASES.md) and implemented in [`relay/sessionorder_test.go`](file:///home/m/dev/pumasi-tunnel/relay/sessionorder_test.go) construct deterministic synchronization barriers rather than relying on timing races:

- **C-1 ([`TestVisitorIsNotAnsweredBeforeTheSessionExists`](file:///home/m/dev/pumasi-tunnel/relay/sessionorder_test.go#L189-L241)):**  
  Holds the relay inside the announce write via `gatedConn`. A visitor request is dispatched and confirmed inside `ServeHTTP` via the `entered` channel. The case asserts that the visitor is not answered during `announceHold` (blocking on `r.mu.RLock()`), and that upon releasing the announce, the request resolves with HTTP `200`. At `8540b89`, this fails deterministically in 0.00s with HTTP `404`.
- **C-2 ([`TestTheAnnounceReachesTheAgentBeforeAnyStream`](file:///home/m/dev/pumasi-tunnel/relay/sessionorder_test.go#L250-L284)):**  
  Dispatches a visitor during a held announce and verifies that the agent receives and decodes a valid `AuthResponse` as its first frame. Against a bare reorder (installing session without holding `r.mu` across the write), this fails deterministically as the visitor's `FrameOpen` reaches the agent first.
- **C-3 ([`TestAFailedAnnounceLeavesNothingBehind`](file:///home/m/dev/pumasi-tunnel/relay/sessionorder_test.go#L323-L468)) & Amendment 1 ([`SPEC.md` §7](file:///home/m/dev/pumasi-tunnel/spec/0003-session-before-announce/SPEC.md#L214-L257)):**  
  Amendment 1 directly addressed the L-006 finding raised by Qwen in the prior review iteration. Rather than merely checking post-cleanup state, C-3 queues a visitor on `r.mu` while the relay is held in a failing announce write. Under Go's `sync.RWMutex` reader-grant semantics, releasing the write lock hands execution to the queued reader before any subsequent `Lock()` can be acquired. If deletion were attempted in a second critical section (violating §3.3), the visitor would be handed a dead session and receive HTTP `502`. With single-critical-section deletion, the visitor sees `session == nil` and receives HTTP `404`. C-3 fails 20 out of 20 times against a two-critical-section implementation, verifying that it directly exercises the exact §3.3 clause it names.
